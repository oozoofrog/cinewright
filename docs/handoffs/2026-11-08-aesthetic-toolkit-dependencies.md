# Implementation dependency and asset decisions

The implementation reuses Node ESM, the manifest-v1 timeline/compositor/freeze/jobs/FFmpeg pipeline, existing motion seeded hash, writeOwnedFiles ownership preflight and installed Three0.180.0. No production package/lockfile dependency was added. Node in the execution receipts: v26.12.1; playwright-core1.64.1; Chromium157.0.8103.38; FFmpeg/ffprobe9.0.2. Three r180 is MIT; playwright-core is Apache-2.0. Native Canvas2D/Path2D has no copied third-party brush library. Original authored cutouts/strokes/UV meshes/clips are declared CC0-1.0 in their own provenance; this does not replace code dependency licenses. FFmpeg/Chrome are runtime executables reported by doctor, not copied or relicensed by this package.

Canvas2D was selected for per-mark pressure/glaze/mask composition and cutout paths without a new retained graphics/UI stack. Three was already installed and supplies actual cameras, light/shadow, UV surfaces, local GLTFLoader and AnimationMixer. The allowlisted r180 GLTFLoader→BufferGeometryUtils transitive closure is copied into project/vendor with LICENSE/version metadata; frozen core remains local vendor/three. No WebGPU/TSL/latest-version mixing or compressed decoder was added. Embedded rigid GLB is the deliberate compatibility boundary.

Rough.js was not needed for authored pressure/reveal/erasure banks; sketch perturbation would not provide these contracts. Paper.js was not needed for authored paths and bounded cubic flattening; there is no claimed boolean/path-reconstruction system. PixiJS would add another GPU renderer and resource model for current Canvas-scale workloads. GSAP was not selected because absolute frame/pose evaluation already exists and avoids stateful timeline callbacks/fades. Inkwell was not selected because the limited UV hatch/rigid outline/light combination can be implemented against the existing pinned Three renderer; no full NPR framework or arbitrary surface direction field is claimed. These are implementation scope/maintenance choices, not benchmarked claims that the candidates are slower or inferior.

For the repository-local skill validator only, a private venv in .direction/aesthetic-toolkit-2026-11-08/validation-venv uses PyYAML6.0.3 (MIT) because the existing validator failed with missing yaml. This is not a production dependency or global installation. quick_validate.py subsequently reported Skill is valid. A/B original authoring scripts record the exact running Python version in payload provenance; C metadata records the Node/Three authoring versions and payload hashes.

Machine: macOS27.2 build26B123, Mac16,11, 24GiB RAM,12 logical CPUs. Browser launch explicitly selects SwiftShader software WebGL2. Validation timings are synchronous draw submission/Canvas composite after warm-up at the recorded size, not GPU-completion timings. Actual GPU memory is unavailable and remains unmeasured. Same-environment seek PNG equality does not imply equality across physical GPUs/OSes.

Recheck correction: alpha image materialization now reuses the installed Chromium decoder through the existing execution.browser helper. It opens a short-lived client with external requests blocked, validates SVG XML and Image.decode plus dimensions, then closes it before publication. This adds no package but means alpha style creation requires the existing Chrome dependency, as playback already does. No WebGL context or server is created for decoding. Binary/image validation receipts remain distinct from image provenance/license statements.
