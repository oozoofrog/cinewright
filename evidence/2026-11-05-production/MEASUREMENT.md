# 제한된 성능 측정 계획

이 계획은 측정 실행 전에 기록했다. [고정 입력과 탐색 인덱스](measurement-plan.json)를 각 실행에 그대로 사용한다. 출력 렌더·재생 담당 작업이 종료됐다는 리더 확인 뒤 실행한다.

| 조건 | 컷 | 고유 SVG | 컷에서 자산을 다시 참조하는 횟수 | 프레임 | 반복 |
| --- | ---: | ---: | ---: | ---: | ---: |
| baseline-4 | 4 | 4 | 0 | 96 | 3 |
| reused-24 | 24 | 4 | 20 | 576 | 3 |
| unique-24 | 24 | 24 | 0 | 576 | 3 |

모든 입력은 320×180, 24fps다. 컷은 각각 24프레임이며 `every: 1`이다. 자산은 같은 구조의 자체 합성 64×36 SVG다. 한 원화 레이어에서 `contain`으로 배치한다. 실작품 자산이나 복잡한 장면을 대표하지 않는다. 각 조건에서 새 Node worker와 새 headless Chrome을 세 번 시작한다. 조건 순서는 표 순서다. 반복 순서는 1→2→3이다.

## 탐색 순서

| 조건 | 지정 순방향 8회 | 역방향 8회 | 미리 고정한 임의 순서 8회 |
| --- | --- | --- | --- |
| baseline-4 | 0,23,24,47,48,71,72,95 | 95,72,71,48,47,24,23,0 | 63,4,88,21,50,9,74,35 |
| 두 24컷 조건 | 0,23,24,143,144,287,288,575 | 575,288,287,144,143,24,23,0 | 383,26,531,127,302,59,447,211 |

각 실행은 frame 0을 확인한 뒤 위 세 순서를 차례로 사용한다. 별도 워밍업은 없다. 임의 순서는 실행 때 다시 추첨하지 않는다. 24컷 입력의 전체 영상은 렌더하지 않는다.

## 시간 범위

fixture 생성·freeze·기존 mixer의 무음 준비는 조건당 한 번이다. 각 단계 시간을 별도로 남긴다. worker·브라우저 시작과 페이지 생성은 탐색 시작 전이다.

- **탐색→준비:** Node의 `performance.now()`를 `page.goto(waitUntil: 'domcontentloaded')` 직전에 읽는다. `window.direction.status().frame === 0`을 확인하는 대기가 반환되면 끝낸다. 페이지 요청, import, 자산 로드, 첫 draw, 대기·프로토콜 비용을 포함한다.
- **탐색→첫 frame 0 readback:** 같은 시작점에서 frame 0의 상태와 `canvas.toDataURL('image/png')`가 Node로 돌아온 시점까지다. PNG 인코딩과 프로토콜 전송을 포함한다. 물리 화면에 표시된 시각은 측정하지 않는다.
- **seek+readback:** 한 `page.evaluate` 안에서 `direction.seek(index)` 후 전체 Canvas를 PNG로 읽고 draw 상태와 PNG 문자열을 반환한다. 호출 직전부터 반환 직후까지를 측정한다. pause·draw·audio currentTime 대입·PNG 인코딩·직렬화·프로토콜 전송을 포함한다. 오디오 seek 완료, 화면 주사, 디스크 쓰기·해시·검증, RSS·파일 순회는 제외한다.

`browser()`의 기존 SwiftShader·자동재생 플래그를 사용한다. viewport는 640×480, deviceScaleFactor는 1이다. Canvas readback은 320×180이다. 새 브라우저 프로필을 사용하지만 OS 파일 캐시를 비우지 않는다.

## 메모리와 디스크 범위

RSS는 새 Node worker와 그 시점의 Chrome/Chromium 하위 PID에 대한 `ps` 스냅샷이다. 단위는 KiB다. 브라우저 전·시작 직후·frame 0·각 8회 탐색 뒤·종료 뒤에 측정한다. PID, PPID와 실행 파일명만 기록하며 전체 프로세스 인수는 남기지 않는다. coordinator Node와 다른 앱은 제외한다. 종료했거나 재부모화된 프로세스는 포착하지 못한다. 합계는 공유 페이지를 중복 계산할 수 있으며 peak RSS나 고유 물리 메모리가 아니다.

디스크는 `task-5-measurement/fixtures/<조건>`, `stores/<조건>`, `audio/<조건>`, `tmp/<조건>-r<회차>`, `runs/<조건>-r<회차>`의 **일반 파일 논리 바이트**다. fixture, 고정 store와 무음은 보존 자료다. run에는 PNG와 로그가 남는다. TMPDIR는 일시 브라우저 자료다. symlink는 따라가지 않는다. 순회 중 사라진 파일도 수에 남긴다. freeze·무음 준비 뒤와 RSS와 같은 실행 단계에서 측정한다. 전체 측정 폴더의 마지막 크기는 누적 감사 수치이며 조건 간 비교에 쓰지 않는다.

브라우저 종료 때 Playwright의 정상 정리를 사용한다. 남은 TMPDIR 파일과 증거는 직접 지우지 않는다. repo 밖 OS 임시 파일·캐시·swap, APFS 실제 할당량은 측정하지 않는다. 폴더 순회는 원자적이지 않다.

## 실행과 실패

작업 저장소 루트에서 `task-5-launch-tmp`를 만든 뒤 JSON에 기록한 명령을 한 번 실행한다. 측정 코드는 기존 결과 디렉터리가 있으면 중단한다. 전체 npm 검사나 영상 렌더를 다시 실행하지 않는다. 실패하면 부분 JSON·stdout·stderr·브라우저 event를 보존한다. 원인을 설명한 뒤 필요한 재시도만 별도 기록으로 수행한다. 수치를 좋게 만들기 위한 반복은 하지 않는다.

결과에는 실행별 값과 단순 최소·중앙값·최대만 적는다. 세 조건의 관찰로 일반 확장성이나 성능 보장을 추론하지 않는다.
