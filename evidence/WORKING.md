# 구현 기록

고정 조건은 상위 정본의 12개 절, 전용 경로, 기존 작업 보존, 로컬 검증이다. 전개 가설과 기술 선택은 이 세션이 정했다.

## 구조 비교

- **신호의 항구**. 하나의 짧은 파형을 종이 해안에 처음 놓는다. 굴절하는 물체가 파형의 방향을 바꾸고, 그 방향이 해안에 돌아왔을 때 항로가 생긴다. 낮은 음과 간격을 둔 타격음은 공간의 척도를 바꾼다. 원화·벡터·3D의 결합이 관객에게 하나의 사건으로 보이는지가 미해결이다.
- **인쇄기**. 색과 글자와 타격음이 즉시 일치한다. 같은 길이의 구절을 반복하지만 한 번씩 행과 칸의 규칙이 달라진다. 감각의 밀도와 동기화가 작품을 이끈다. 마지막의 단정한 정렬이 쾌감으로 읽힐지 검토한다. 러프 반례로 선택했다.
- **조석 관측**. 대상 없이 선의 밀도와 수평선의 높이가 천천히 이동한다. 반대로 오디오는 짧은 구획을 만든다. 매체 사이의 사건 교환 없이 장기적인 대비를 시험할 수 있다. 이번 검증 묶음에서는 앞의 두 안이 교환 유무와 전개 차이를 더 직접적으로 시험한다.

## 도구 선택

- 브라우저 Canvas 2D와 ES 모듈을 공통 합성 경계로 택했다. 3D 모듈은 Three.js에서 카메라·조명·형상을 평가한다. Chromium에서 같은 평가기를 대화형과 오프라인으로 실행한다. FFmpeg는 샘플 기준 오디오 배치와 MP4 인코딩을 맡는다. CLI는 스킬의 로컬 파일 제작 및 실패 기록에 맞고 MCP 서버 등록을 요구하지 않는다.
- 단일 통합 3D 타임라인은 카메라와 깊이가 불필요한 그림·인쇄 전개에도 공간 모델을 강제한다. 매체별 영상만 합치는 방식은 재생 비용이 낮지만 교환 값 변경마다 별도 렌더와 자산 교체가 필요하다. 현재 구조는 사전 계산 값도 받을 수 있다.
- Python 이미지 합성은 이 환경의 Pillow로 가능하다. 브라우저와 이중 평가기를 유지해야 하므로 제외했다. Blender 실행 파일은 초기 PATH에 없었다. 런타임 3D는 Three.js로 시험한다.
- Showreel 기준 커밋은 ae09a4a757b6e1d22c4193a09c70c88bda5b3e92. [소스](https://github.com/revfactory/showreel/tree/ae09a4a757b6e1d22c4193a09c70c88bda5b3e92)
  - 문서의 구간별 이미지·운동·음악 큐 설계와 실제 출력 QA를 참고했다. `references/{brief,story,design,audio,qa}.md`.
  - `references/engine.md`는 절대 시각 평가와 시뮬레이션 사전 계산을 권한다. `assets/engine/engine.js`의 `seek`와 `scripts/render.mjs`는 임의 시각 렌더 호출을 구현한다.
  - 장면별 모듈과 장면 로컬 시각을 채택하지 않았다. Showreel은 소스 조사만 했다. MIT 소스는 복사하지 않았다.
